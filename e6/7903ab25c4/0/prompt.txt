## Full Spec Constraints
[
  "The existing Hermes agent uses Google Gemini 2.5 Flash via OpenRouter \u2014 all new agent actions must work through this same LLM gateway",
  "Write tools follow the proposal-envelope pattern \u2014 they propose actions for human confirmation, never execute directly",
  "The SSE streaming infrastructure already exists in the chat engine \u2014 reuse it for action streaming rather than building a parallel system",
  "The seed service must remain idempotent \u2014 safe to run multiple times without duplicating data",
  "The frontend is a Next.js 15 app in a pnpm monorepo with shadcn/ui components \u2014 all new UI must use this stack",
  "The backend uses SQLAlchemy with Alembic migrations and PostgreSQL \u2014 new models require proper migrations",
  "All API responses must follow the existing standardized format with camelCase serialization",
  "The existing /dev/reset endpoint drops all tables \u2014 it must be extended to handle any new models/tables",

Evaluator notes: Sprint 2 implemented a solid architectural foundation for streaming action cards (SSE route, AgentAction model, action-card component, four new write tool types), but two critical bugs prevent the features from working end-to-end in the default configuration. Bug-001 (os.environ vs pydantic-settings) makes the agent permanently fall back to stub mode when started normally with 'python run.py'. Bug-002 (LLM uses display ticket number as tool argument) causes get_ticket() to fail on every invocation, blocking vendor email, tenant response, and owner report actions from ever reaching the proposal stage. Escalation partially works because the LLM skips ahead to escalate_to_human even after get_ticket fails, but Bug-003 makes the Confirm button 404. The UI components (action-card.tsx, escalations page) are well-designed with proper styling and badge states, but Bug-004 prevents live status updates during streaming. All regression checks pass cleanly. Recommendation: fix agent_runtime.py to use get_settings().openrouter_api_key, and rewrite the user_message in agent_run.py to lead with the internal ticket ID rather than the display number.
